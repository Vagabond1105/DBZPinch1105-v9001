# 05.3 · V3 Phase 4: the curated write-up library

> [!abstract] One-sentence version
> Every analysed run now opens with a short, **hand-written explanation** (*What happened*, *Why*, *Try next*) picked from a fixed library of 20 entries and filled with the run's own numbers. Nothing is generated freely, so the program can't invent physics. Every sweep statistic it quotes is counted from the data, not typed in.

Series: [[05 - V3 Plan]] → [[05.1 - V3 Phase 1 Results]] → [[05.2 - V3 Phase 3 Machine Learning]] → **05.3 Phase 4 Write-up Library**

Built 2026-10-20 (Claude wrote the code and the entries; see [[05 - V3 Plan#Status (2026-10-20)|who builds what]]). Tests: 30 new (`v2/tests/test_library.py`).

---

## 1. What Phase 4 is for

After Phase 1, a report already said *what* happened and gave the energy bookkeeping. But it read like a lab log: "Paid for by the magnetic field (6 % of E0); it went into heat (thermal) (4 %) …". Phase 4 puts a readable explanation on top, written the way notes 01–04 are written, for a student who has never met a Z-pinch.

The plan ([[05 - V3 Plan]] §7) set three rules:

1. **No free text generation.** Every sentence is written once, by hand, and checked. Only the numbers change from run to run.
2. **Pick the closest entry, and say how close.** A library can't have an entry for every combination of settings.
3. **Unreviewed entries never ship.**

---

## 2. How it works

| File | What it does |
|---|---|
| `v2/zpinch/analysis/library/*.md` | **The 20 entries.** Each has a front-matter header (which class, which parameter box, an example run, a GUI preset) and three sections of text with `{placeholders}`. |
| `v2/zpinch/analysis/writeup.py` | Loads the entries, **picks one** for a run, fills in the numbers. |
| `v2/zpinch/analysis/library/stats.json` | For each entry, how the sweep runs in its box turned out. Generated, never edited by hand. |
| `v2/zpinch/analysis/library/examples.json` | The starting parameters of each entry's example run, so the program can load them without the dataset. Generated. |
| `v2/tools/library.py` | `stats` (recount), `suggest` (find good example runs), `check` (every entry on its example), `show` (print one run's write-up). |
| `v2/tests/test_library.py` | 30 tests: every entry parses and fills, every class has a general entry, the selection rule, and each example run picking its own entry. |

### An entry, as stored

```markdown
---
id: saturated-kink-marginal
class: saturated_kink
title: Saturated kink just inside the Kruskal-Shafranov limit
regime: nq_seed 0.5..1.0
compare: nq_seed 0.5..1.0; gravity 0..0.3; cooling 0..0.3
example: r00273
preset: Saturated kink (Bz = 0.6)
reviewed: data-checked
---
## What happened
The column bent into a corkscrew that grew for a while and then stopped,
levelling off at about {m1_sat:.2f} radii (t = {t_sat:.2f}) ...
## Why
... In the overnight sweep, {regime_same} of the {regime_runs} runs in this
band (n q from 0.5 to 1, little gravity or cooling) saturated like this.
## Try next
Raise B_z to {bz_stable:.2f} (n q = {nq_stable:.2f}) and the kink should not grow at all ...
```

`{m1_sat:.2f}` means "this run's saturation level, two decimals". The placeholders are the 65 features from Phase 1, the evidence the rules used, the phase times, and a few computed extras. For example, `bz_stable` is the axial field that would put this column's seeded helix at n q = 1.5.

### Picking an entry

1. Keep the entries of the run's class (the label comes from the Phase 1 rules).
2. Keep those whose **regime box** contains the run. A box is a range for one or more features, like `nq_seed 0.5..1.0`.
3. Of those, the **most specific** wins (most box conditions; ties broken by `priority`).
4. A class's **general entry** has no box, so it always qualifies, but any regime entry beats it.

A regime entry is **never used outside its box**. Its text states facts about the regime ("with no axial field, nothing resists bending"), and those would be false outside it. When no regime entry fits, the report uses the general entry and names the nearest regime entry, with how far outside its box the run is.

### Numbers quoted from the sweep stay true

Sentences like "70 of the 70 runs in this band saturated" are not typed into the text. They are `{regime_same}` and `{regime_runs}` placeholders, filled from `stats.json`, which `tools/library.py stats` counts from the labelled sweep. When the sweep grows, one command updates every quoted number.

Each entry counts the runs in its **compare box**. That's usually its regime box narrowed to runs where nothing else interferes. Without that, a Kruskal–Shafranov count ("runs with n q above 1.5") would be mostly gravity-sag runs, because gravity knocks the column sideways whatever n q is. The text always says which runs it is quoting ("little gravity or cooling").

**Example runs** are the "textbook runs": a clean run (high confidence, no numerical-health flags, finished) near the middle of the entry's box. `tools/library.py check` re-analyses each one and fails unless it gets the entry's class, picks that entry, and fills every number. The general entries for the common classes have no example, because a regime entry always covers sweep runs first. The *kink still growing* and *too early* entries can't have a sweep example, because every sweep run went to t = 3. These entries are tested on synthetic runs instead.

**Presets:** each GUI preset was run headless to t = 3 (2026-10-20) and analysed. *Pure Z-pinch* → disruption (low confidence: the column spread 0.90 time units after the kink went nonlinear, against a cut-off of 1). *Saturated kink (Bz = 0.6)* → saturated kink. *Stable screw pinch* → quiescent. *Implosion (snowplow)* → disruption, with a compression phase. Each matches the entry that names it. *Gravity sag* (B_z = 0, g = 1) ends as a **disruption** by t = 3, with the sag only secondary: without an axial field the kink takes over. So it names no entry; guide T8's numbers are taken at t = 0.6, when it is still a sag. A sag that lasts needs a kink-stable B_z (example run r00141: B_z = 1.29, g = 1.43).

## 4. What writing the entries found

Checking every sentence against the data turned up five things. Two were mistakes in earlier phases.

1. **A blind spot in the helix diagnostic (Phase 1 bug, fixed).** The saved history measures the kink in the n = 1, 2, 3 helices only. A column seeded with n ≥ 4 (anything longer than about 2.1 at the default radius) keeps its kink in a helix the diagnostic can't see, so all three read zero. The feature `m1_dominant_n` then took the "largest of three zeros" and reported **n = 1**. The report told 287 runs "not the n = 4 that was seeded: this helix outgrew it", which was false. Fixed: the dominant n is now *unknown* when n = 1–3 carry less than half the kink, a new feature `m1_resolved_frac` records the share, and the text says what the diagnostic can and can't see.
2. **So the seed really does pick the helix.** With the blind spot removed, the kink stays in the seeded helix in **all 529** runs the diagnostic can resolve. [[05.1 - V3 Phase 1 Results]] §7 said "529 of 816" and is corrected. No run showed a longer helix taking over, so no entry claims one does.
3. **Why kinks still grow just above n q = 1.** Kruskal–Shafranov compares the field-line twist with the helix at the column's **edge**. For the Bennett profile, $B_\theta \propto r/(r^2 + a^2)$, so $q(r) \propto r^2 + a^2$: **on the axis, q is half its edge value.** For 1 < n q < 2 the inner column is below the line and can kink, while the outer part holds it. That matches the data: kinks above n q = 1 are about half the size of those below (median peak 0.18 a against 0.37 a). It is also why the stability line in the sweep sits near 1.5, not 1. The axis argument alone would put it at 2; dissipation and the short run account for the rest.
4. **Radiative collapse needs the kink held off.** With strong cooling (C ≥ 0.9), none of the 59 runs with n q < 0.5 collapsed. The kink tore them apart first. With n q ≥ 0.5, 30 of 68 did. The collapse entry explains it that way.
5. **"Try next" has to stay on the sliders.** At the default column length the B_z for n q = 1.6 would be 1.59, above the slider's 1.5. The stable target is n q = 1.5, where the sweep's no-kink band starts, which needs at most 1.49 at the default radius. If a user's radius makes a suggestion leave the slider range anyway, the report says so.

## 5. Review status (honest)

All 20 entries are marked **`data-checked`**: Claude checked every claim against the sweep statistics and the example runs, and against notes 01–04. **None is marked `yes`**: no physicist has read them yet. The report says this on every run ("checked against the sweep data; not yet reviewed by a physicist"). The plan's rule "unreviewed entries never ship" is kept in code: an entry marked `no` is never used.

To review one, see `v2/zpinch/analysis/library/README.md`: print it filled in, check each sentence of *Why* and each *Try next*, then change the line to `reviewed: yes`.

## 6. How to use it

From `v2/`:

```bash
.venv/bin/python tools/analyse.py dataset/sweep-2026-10-19/runs/r00273.npz      # full report
.venv/bin/python tools/library.py show dataset/sweep-2026-10-19/runs/r00273.npz # write-up only
.venv/bin/python tools/library.py stats dataset/sweep-2026-10-19                 # after relabelling
.venv/bin/python tools/library.py check dataset/sweep-2026-10-19                 # every entry on its example
./run.sh --headless --t-end 3 --preset "Stable screw pinch" --analyse
```

## 7. Honest limits

- **The library covers regimes, not every combination.** A run with heavy cooling *and* gravity *and* a strong drive gets the entry for its class and its most specific matching box. That entry is true for the run, but it may not mention everything that happened. The data appendix underneath always has the full timeline.
- **The quoted statistics are 32³ runs from one sweep.** They are counts, not probabilities for a new run. The outcome predictor (Phase 3) gives those.
- **Kinks of n ≥ 4 are invisible to the saved diagnostic.** A future sweep could record n = 4–6 too; the solver computes them, but the history keeps only n = 1–3.
- **The general entries for the common classes are reached only as fallbacks**, so they are tested on synthetic runs, not on real ones.
